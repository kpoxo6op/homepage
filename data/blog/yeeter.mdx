**Status: Dead**

YEETer was an experiment from April 2026. A seller took one photo of an item and the app generated a Trade Me listing draft: title, category, description, price, shipping, and category attributes. The seller could review and edit everything before explicitly confirming the listing.

The app used Trade Me OAuth. It did not collect Trade Me passwords, and its tokens and API secrets stayed on the server.

The complete flow worked. YEETer created a real Trade Me test listing, which was then withdrawn.

## Using OpenAI twice

OpenAI was involved in two different parts of YEETer.

The obvious one was inside the application. YEETer sent the photograph to an OpenAI vision model and requested structured data containing a proposed title, object type, category candidates, condition, material, visible text, a search phrase, and a confidence score. If the smaller model returned less than 72% confidence or said that the seller needed to choose, the backend tried a larger model. A low-confidence result was supposed to ask the seller for help instead of inventing details.

The more entertaining use was during development. I took screenshots from the real Android application and gave them to ChatGPT. It returned complete annotated design boards showing what was wrong with the interface and how to restructure it.

These boards are more useful here than screenshots of source code. A code screenshot would only prove that the application contained an OpenAI API call. Each board shows the real phone interface, the problem ChatGPT found, and its proposed solution in one image. They document the development loop itself: screenshot the current build, ask the model to inspect it visually, receive a redesigned version with annotations, implement it, and test the next build on the phone.

They are also artifacts produced by the same AI-assisted process the project is about. OpenAI was not only generating data inside YEETer. It was looking at YEETer from the outside and helping redesign the application around that data.

This was the first time image generation felt like a practical software-development tool to me. Instead of receiving another page of design advice, I received an image of my own application covered in proposed corrections. I could compare it with the phone in my hand, change the app, take another screenshot, and continue.

## Completely vibecoded

The application was completely vibecoded. I told Codex CLI to use `scrcpy` to operate the Android phone from my laptop and keep iterating on the real application.

Codex navigated the screens, captured screenshots, inspected the Android UI, changed the code, installed another build, and repeated the flow. Its vision caught many stupid visual and navigation bugs directly from the phone. I did not need to notice each bug, describe it in words, or explain where on the screen it appeared.

The repository contains a large collection of screenshots from these passes: camera states, loading screens, review layouts, keyboard problems, back-navigation behaviour, header spacing, footer overlap, the app icon, and the final standalone build. Most of this work happened over a few days.

## How far the prototype got

The repository began on 22 April 2026. By 24 April, the phone could capture a real image and send it to a Cloudflare backend. OpenAI produced the draft, and the app grounded the proposed category against Trade Me sandbox data.

The integration covered Trade Me OAuth, account verification, category search and details, photo upload, listing validation, and fee calculation. OpenAI and Trade Me secrets stayed on the backend rather than inside the Android application.

The app was also built and installed as a standalone Android APK. It did not require Expo Go, a development server, or a laptop to launch.

One sandbox problem had nothing to do with AI. The test seller account had Ping enabled, while some General Items categories reported Cash as their allowed payment method. Trade Me rejected the validation even when YEETer explicitly sent Cash. The repository records this as a sandbox account or category conflict.

The final guarded version deliberately kept automatic listing creation disabled. It could upload the photo, validate the proposed listing, calculate fees, and show everything for review, but the final create action stayed behind the unfinished **YEET!** button.

I applied for production API access on 24 April 2026. The Trade Me developer portal later showed that the production API application was marked as declined, without an explanation.

On 30 April I asked Trade Me what had caused the decision and whether a restricted version would be acceptable. I offered to limit it to invited New Zealand sellers and General Items, and explained the safeguards: no automatic posting, no scraping, no market-data aggregation, no price comparison, no retained expired listings, and no Trade Me branding.

The reply only said that the address I had contacted handled the Property API and redirected Marketplace questions to another address. I found no later answer or reason for the decline.

The app worked, but it could not become a real product without production API approval, so the project ended there.
